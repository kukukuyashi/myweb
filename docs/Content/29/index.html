1. Git 与 GitHub 是什么

Git

Git 是一个分布式版本控制系统（Version Control System, VCS）。

通俗理解：它像给代码做的「时光机 + 存档系统」——每次保存（提交）都会留下一个快照，你可以随时回到任意历史版本，对比差异，多人并行修改而不互相覆盖。

概念 解释
版本控制 记录文件每次变更的历史，支持回退、对比、合并
分布式 每个开发者本地都有完整仓库副本，不依赖单一中央服务器也能工作
仓库（Repository / Repo） 存放项目代码及全部历史记录的目录，含隐藏的 .git 文件夹

GitHub

GitHub 是一个基于 Git 的代码托管平台（Remote Hosting Platform）。

对比 Git GitHub
本质 工具 / 软件 网站 / 服务
作用 在本地管理版本 在云端存储、分享、协作
关系 引擎 停车场 + 协作平台

GitHub 还提供：Pull Request（代码审查）、Issues（任务跟踪）、Actions（CI/CD 自动化）、Pages（静态网站托管）等。

2. Commit 提交

什么是 Commit

Commit（提交） 是一次「快照」，把暂存区的改动永久写入本地仓库历史。

每次提交包含：

  • Commit ID（哈希值 / SHA-1）：如 a3f2c1d...，40 位十六进制字符串，全局唯一标识该提交
  • 作者、时间
  • 提交说明（Commit Message）：描述「为什么改」，而非仅「改了什么」
  • 父提交指针：形成历史链

git log --oneline    # 查看简洁提交历史
git show <commit-id> # 查看某次提交详情

三种「撤销/回退」方式对比

这是初学者最容易混淆的部分：

操作 命令示例 影响范围 是否改历史 已 push 后是否安全
Discard（丢弃） git restore <file> 或 git checkout -- <file> 仅工作区未暂存的修改 否 安全（仅本地未提交内容）
Reset（重置） git reset --soft/mixed/hard <commit> 移动 HEAD 指针，可选改工作区/暂存区 是（改写本地历史） 危险（若已 push，需 force push）
Revert（还原） git revert <commit> 新建一个反向提交来抵消某次提交 否（追加新提交） 安全（适合已共享的历史）

Discard — 丢弃未提交的本地修改

行为：把文件从最后一次 commit 的状态恢复回来，未 commit 的改动会丢失。


git restore src/data/posts.js          # 丢弃工作区修改
git restore --staged src/data/posts.js # 取消暂存（保留工作区修改）

场景：

  • 改错了文件，还没 git add，想恢复原样
  • 误 git add，想从暂存区撤出

Reset — 重置到某个提交

行为：把当前分支的 HEAD 移到指定 commit，之后的历史在本地「消失」（ reflog 可找回一段时间）。

三种模式：

模式 HEAD 暂存区 工作区
--soft 移动 保留 保留
--mixed（默认） 移动 清空 保留
--hard 移动 清空 清空 

git reset --hard HEAD~1   # 回退 1 个提交，工作区也清空（慎用！）
git reset --soft HEAD~1   # 回退提交，改动保留在暂存区

场景：

  • 本地刚 commit，发现 message 写错或漏文件 → --soft 后重新提交
  • 本地多个 commit 想合并成一个 → 交互式 rebase 或 soft reset
  • 仅限本地、未 push 的历史整理

⚠️ 不要对已经 push 到远端的 commit 做 --hard reset，除非团队明确同意并使用 force push。

Revert — 反向提交

行为：不删除历史，而是创建一个新 commit，内容与指定 commit 相反（相当于「撤销那次提交的改动」）。


git revert abc1234

场景：

  • 某次有问题的 commit 已经 push 到 main
  • 生产环境需要撤销某功能，但保留完整审计历史
  • 开源项目 / 团队协作的标准做法

记忆口诀


Discard  →  还没 commit，扔掉本地改动
Reset    →  改本地历史，像时光机倒带（未 push 用）
Revert   →  不改历史，用新提交「对冲」旧提交（已 push 用）

3. Branch 分支

什么是 Branch

Branch（分支） 是提交历史的一条独立线。默认主分支通常叫 main（旧项目可能是 master）。


main:     A --- B --- C --- D
                \
feature:         E --- F

分支让多人/多功能并行开发，互不干扰，最后再通过 merge（合并） 汇合。

常用命令


git branch              # 列出本地分支
git branch feature-x    # 创建分支
git checkout feature-x  # 切换分支
git switch -c feature-x # 创建并切换（推荐）
git merge feature-x     # 把 feature-x 合并进当前分支
git branch -d feature-x # 删除已合并的分支

分支策略（简单版）

分支 用途
main 稳定、可部署的代码
feature/xxx 新功能开发
fix/xxx Bug 修复
gh-pages 本项目 GitHub Pages 部署分支（由 Actions 自动维护）

4. Worktree 与 Merge Conflict

Worktree 是什么

Worktree（工作树） 在 Git 里有两层含义，初学者先掌握第一层：

  1. 日常含义：你正在编辑的文件所在目录 = 工作区（Working Directory），即项目文件夹里肉眼可见的文件
  2. 进阶命令 git worktree：在同一仓库下，同时检出多个分支到不同目录，避免频繁 checkout 切换

# 进阶：在同一 repo 开第二个工作目录
git worktree add ../gerenboke-hotfix hotfix-branch

适用场景：main 上在开发大功能，突然要修线上 bug，不想 stash 当前改动，可以另开一个目录处理 hotfix。

Merge Conflict（合并冲突）

Merge Conflict（合并冲突） 发生在：两个分支修改了同一文件的同一区域，Git 无法自动决定保留哪边。

冲突标记示例：


<<<<<<< HEAD
const title = '版本 A'
=======
const title = '版本 B'
>>>>>>> feature-x

解决冲突步骤

  1. git merge feature-x 或 git pull 后提示冲突
  2. 打开冲突文件，手动编辑，删除 <<<<<<<、=======、>>>>>>> 标记
  3. git add <已解决文件>
  4. git commit 完成合并提交

减少冲突的建议

  • 小步提交、频繁 pull / rebase
  • 功能按模块分工，少改同一文件
  • 合并前先 git fetch + 本地测试

5. Git 分区（四个区域）

Git 的核心是理解数据在四个区域之间如何流动：


┌─────────────┐    git add     ┌─────────────┐   git commit   ┌─────────────┐
│  工作区      │  ──────────►  │  暂存区      │  ──────────►  │  本地仓库    │
│ Working Dir │               │ Staging     │               │ Local Repo  │
│ (可见文件)   │  ◄──────────  │ (Index)     │               │ (.git)      │
└─────────────┘  git restore  └─────────────┘               └──────┬──────┘
                                                                  │
                                                     git push     │  git pull / fetch
                                                                  ▼
                                                           ┌─────────────┐
                                                           │  远程仓库    │
                                                           │ Remote Repo │
                                                           │ (GitHub)    │
                                                           └─────────────┘
区域 英文 说明 对应命令
工作区 Working Directory 磁盘上正在编辑的文件 直接改文件
暂存区 Staging Area / Index 下次 commit 要包含的内容 git add / git restore --staged
本地仓库 Local Repository .git 内的完整历史 git commit / git log
远程仓库 Remote Repository GitHub 上的副本 git push / git pull / git fetch

关键关系

  • git status：查看工作区 vs 暂存区 vs 最后一次 commit 的差异
  • git add：工作区 → 暂存区（「打包待提交」）
  • git commit：暂存区 → 本地仓库（「正式存档」）
  • git push：本地仓库 → 远程仓库（「上传到 GitHub」）
  • git pull = git fetch + git merge：远程 → 本地（「拉取并合并」）

你终端里看到的状态（对照本项目）


Changes not staged for commit:   → 工作区有改动，还没 git add
Changes to be committed:         → 已在暂存区，等待 git commit
Untracked files:                 → 新文件，Git 尚未跟踪
Your branch is up to date with 'origin/main'  → 本地 main 与远程同步

6. 远端仓库实战（以本项目为例）

本项目 gerenboke 是 Vue 3 个人博客，远程仓库为 kukukuyashi/myweb，通过 GitHub Actions 推送到 main 后自动构建并部署到 GitHub Pages。

在线地址：<https://kukukuyashi.github.io/myweb/>

6.1 从零新建类似项目


# 1. 在 GitHub 网页创建空仓库 myweb（不要勾选 README 若本地已有项目）

# 2. 本地初始化
cd D:\phpstudy\phpstudy_pro\WWW\gerenboke
git init
git branch -M main

# 3. 关联远程
git remote add origin https://github.com/kukukuyashi/myweb.git

# 4. 首次提交
git add .
git commit -m "init: Vue3 博客项目"
git push -u origin main
术语 解释
origin 远程仓库的默认别名
-u 建立 upstream，之后可直接 git push / git pull

6.2 克隆已有项目


git clone https://github.com/kukukuyashi/myweb.git
cd myweb
npm install
npm run dev

6.3 日常修改与发布（博客发文章流程）

结合 README 与本项目结构：


1. Content/           放入文章 HTML
2. src/data/posts.js  注册文章元数据
3. npm run build      生成 docs/ 静态产物
4. git add + commit + push
5. GitHub Actions 自动 build 并部署到 gh-pages

示例：


# 改完 posts.js 和 Content 后
npm run build

git status                              # 确认 docs/ 等变更
git add Content/ src/data/posts.js docs/
git commit -m "post: 新增 Agent Harness 体系笔记"
git push

6.4 本项目的 .gitignore 要点

以下内容不会被 Git 跟踪（不应 commit）：

路径 原因
node_modules/ 依赖，用 npm install 恢复
笔记/* 本地 Markdown 原稿（除个别例外）
Music/ 音乐源文件走 CDN，不进 Git
.env 含密钥，绝不提交

你终端里 笔记/Agent/Agent Harness 体系.md 在本地，但 .gitignore 会忽略 笔记/*；发布到博客的是 Content/ 下的 HTML 和 build 后的 docs/。

6.5 查看远程状态


git remote -v           # 查看远程 URL
git fetch origin        # 只下载远程更新，不合并
git pull                # fetch + merge 到当前分支
git log origin/main     # 看远程 main 的历史

6.6 部署链路（本项目特有）


push main → .github/workflows/deploy.yml 触发
         → npm install && npm run build

         → GitHub Pages 对外提供静态站点

7. GitHub 多人协作与进阶命令

7.1 多人协作基本流程


1. Fork（可选）或直接 Clone 仓库
2. git checkout -b feature/my-feature   # 从最新 main 拉功能分支
3. 开发、commit（小步、message 清晰）
4. git push -u origin feature/my-feature
5. 在 GitHub 创建 Pull Request（PR）→ 目标分支 main
6. Code Review → 修改 → 再次 push（PR 自动更新）
7. Merge PR → 删除功能分支
8. 其他人 git pull 同步 main

7.2 协作注意事项

事项 说明
先 pull 再 push 减少冲突；git pull --rebase 可保持线性历史
不要 force push 到 main 会覆盖他人工作，破坏团队历史
小 PR、单一职责 一个 PR 只做一件事，便于审查
写清楚 PR 描述 改了什么、为什么、如何测试
敏感信息 .env、密钥、Token 绝不 commit；已泄露需轮换密钥
保护 main 分支 在 GitHub Settings 开启「Require PR before merging」
沟通冲突 冲突时与改同一文件的同事对齐，不要静默覆盖

7.3 Stash — 临时贮藏

Stash：把工作区 + 暂存区的未提交改动暂时「藏起来」，工作区变干净，之后可再恢复。


git stash              # 贮藏当前改动
git stash list         # 查看贮藏列表
git stash pop          # 恢复最近一次并删除 stash
git stash apply        # 恢复但不删除 stash
git stash drop         # 删除某条 stash

场景：

  • 功能写到一半，需要紧急切换分支修 bug
  • 想 git pull 但本地有未 commit 改动

7.4 Rebase — 变基

Rebase：把当前分支的提交「挪到」目标分支最新提交之后，形成线性历史。


# merge 方式（保留分叉）:
main:    A - B - C - M
              \     /
feature:       D - E

# rebase 方式（线性）:
main:    A - B - C - D' - E'


git checkout feature-x
git rebase main        # 把 feature-x 的提交接到 main 最新之后
git rebase -i HEAD~3   # 交互式： squash / 改 message / 删 commit

场景：

  • PR 合并前整理 commit（squash 多个 wip commit）
  • 保持 main 历史整洁

⚠️ 黄金法则：不要 rebase 已经 push 且他人可能基于它开发的公共分支。

7.5 Cherry-pick — 拣选提交

Cherry-pick：把某一个（或几个）指定 commit 复制到当前分支，而不是合并整分支。


git cherry-pick abc1234           # 拣选单个 commit
git cherry-pick abc1234 def5678   # 拣选多个
git cherry-pick -n abc1234        # 只应用改动，不自动 commit

场景：

  • main 上修了一个 bug，需要同步到 release 分支
  • 只想拿 feature 分支里的某一个 commit，不要全部

与 merge 的区别：

Merge Cherry-pick
范围 整分支所有差异 指定 commit
历史 产生 merge commit 复制 commit（新 hash）

附录：常用命令速查


# 状态与历史
git status
git log --oneline --graph --all
git diff                    # 工作区 vs 暂存区
git diff --staged           # 暂存区 vs 最后一次 commit

# 基本流程
git add .
git commit -m "message"
git push
git pull

# 分支
git switch -c feature-x
git merge feature-x

# 撤销
git restore <file>

# 进阶
git stash

git cherry-pick <commit-id>
