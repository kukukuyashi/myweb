博客性能优化实录：从 curl 探测到 HTTP/2 与缓存策略

日期：2026-09-14
访客反馈站点打开偏慢。这篇记录一次完整的性能排查与修复流程：不猜原因，先实测线上响应，再逐层定位，最后按收益排序修掉。适合第一次给静态站 + 小水管 ECS 做提速的同学对照。
  • 学会用 curl -sI 和 ALPN 探测验证生产环境真实配置（而不是想当然）
  • 理解 no-store / no-cache / immutable 三种缓存策略的差别
  • 理解为什么 HTTP/1.1 下"每个资源一次 revalidate"会把首屏拖垮
  • 复现"本地文件没提交 → 线上 404"这类部署漂移问题的定位手法

1.1 现象与目标

症状很简单：用户访问 https://cyinc.ink/myweb/ 觉得慢，尤其是第二次打开也不快。这说明问题不只是首次下载量大——缓存根本没生效。

目标：把"慢"拆成可测量的指标，逐项修复，而不是凭感觉加 CDN。

1.2 排查工作流：先测，再猜

第一步：看构建产物，排除明显的打包问题

先确认前端本身有没有低级问题：

  • 路由全部 () => import() 懒加载 ✓
  • manualChunks 把 vue/pinia 拆成 vue-vendor（105KB）、prism、dompurify 独立 chunk ✓
  • 已有缩略图管线 generate-thumbnails.mjs + thumbManifest.json ✓
  • 字体用系统栈，没有外网字体阻塞 ✓

结论：构建侧基本健康，问题大概率在传输层和缓存策略。

第二步：curl 实测线上响应头

仓库里的 deploy/nginx.conf.example 写得挺好，但线上跑的不一定是你以为的配置。直接测：


# 带 hash 的 JS chunk —— 应该 immutable 长缓存
curl -sI https://cyinc.ink/myweb/assets/vue-vendor-DBkQmFS8.js
# 文章目录 —— 前端每次访问都拉
curl -sI https://cyinc.ink/myweb/data/posts.json
# 大图 —— 应该有长缓存
curl -sI https://cyinc.ink/myweb/img/bkm/5.jfif

实测结果：

资源 期望 实际
assets/*.js Cache-Control: immutable 什么都没有，只有 ETag/Last-Modified
data/posts.json 可协商缓存 no-cache, must-revalidate
Content/*.html 可协商缓存 no-cache, must-revalidate
img/* 7d 缓存 ✓ 正常
gzip on ✓ 正常

两处关键问题浮出水面：

  1. assets/ 的 immutable 缓存段线上根本没有——生产 Nginx 配置和仓库示例漂移了。
  2. no-cache 本身没错，但前端 fetch 用的是 cache: 'no-store'，等于把浏览器的协商缓存也绕过了，每次必全量下载。

第三步：确认 HTTP/2 有没有开

curl 的 -I 默认走 HTTP/1.1，看不出协议支持。用 Python 做 ALPN 探测：


import ssl, socket
c = ssl.create_default_context()
c.set_alpn_protocols(['h2', 'http/1.1'])
s = socket.create_connection(('cyinc.ink', 443))
ss = c.wrap_socket(s, server_hostname='cyinc.ink')
print(ss.selected_alpn_protocol())   # 实测输出：http/1.1 —— HTTP/2 没开

第四步：算 TTFB，确认瓶颈不在服务器


curl -s -o NUL -w "ttfb=%{time_starttransfer}s total=%{time_total}s" \
  https://cyinc.ink/myweb/
# ttfb=0.085s —— 服务器响应其实很快

TTFB 只有 85ms，说明慢的不是后端处理，而是"下载调度"：首屏几十个资源在 HTTP/1.1 上只能开 6 个连接，其中大部分又是"问一下变了没"的 304 请求，每个都要占一次往返。

第五步：定位 404 的根因（解析 .git/index）

实测发现 img/xiaoqing-avatar.webp、img/home-ink.webp 线上 404，但本地明明有文件。怀疑是没提交进 git。本机恰好没有 git 命令，直接解析 .git/index 二进制格式列出已跟踪文件：


import struct
data = open('.git/index','rb').read()
# DIRC 头 + 版本 + entry 数，每个 entry = 62字节stat + 路径 + 8字节对齐填充

结果：img/ 下 1041 个跟踪文件里没有这两个文件——9 月 5 日本地加的，从未 commit。ECS 靠 git pull 同步非 BA 的 img，所以线上拿不到，hero 背景和头像全破图。

这类"本地能跑线上 404"的问题，八成是部署漂移：文件存在 ≠ 文件会被同步。查跟踪状态比查文件存在更靠谱。

1.3 修了什么，以及为什么

图片：装饰图全部换 .thumb.webp

墨染头图（首页 hero、归档页、音乐室头图）原来直接用 1MB+ 的 .jfif 原图。这类图被遮罩和渐变盖住，清晰度损失肉眼不可见，换 720px webp 缩略图后 1.1MB → ~80KB，-93%。

头像更夸张：xiaoqing.png 898KB，显示尺寸只有 80px。换成 xiaoqing.thumb.webp 后 898KB → 22KB，-97%，每页都省。

原则：展示尺寸决定该加载什么图。80px 的头像用 2000px 原图是纯浪费。

fetch 缓存：no-store → no-cache


// 改前：每次都全量下载，posts.json 18KB、文章 23KB+
fetch(url, { cache: 'no-store' })

// 改后：带 ETag 回源问一句"变了没"，没变就是 304 空响应
fetch(url, { cache: 'no-cache' })

三个易混的缓存语义：

指令 行为 适用
no-store 完全不进缓存，每次全量下载 敏感数据
no-cache 可以存，但每次用前必须回源验证（ETag → 304） 会变但想省流量的内容
immutable + 长 max-age 存了就别再问 文件名带 hash 的构建产物

之前 posts.json 和文章正文都是 no-store + Nginx no-cache，等于最坏组合：既不缓存又每次全量。改成 no-cache 后，没变的内容只传一个 304 响应头（几百字节）。

Nginx：补齐漂移掉的配置

线上配置和仓库示例已经漂移，按新版示例对齐：

1. 开 HTTP/2（nginx 1.18 用旧语法）：


listen 443 ssl http2;

为什么重要：HTTP/1.1 一个连接一次只能处理一个请求，浏览器对单域最多开 6 个连接。首屏 ~40 个资源 = 排队 7 轮。HTTP/2 单连接多路复用，全部并行。

2. 修复 upstream keepalive：


map $http_upgrade $connection_upgrade {
    default upgrade;
    ''      '';
}
# location /api 里：
proxy_set_header Connection $connection_upgrade;

原配置把 Connection "upgrade" 写死了——本意是支持 WebSocket，副作用是普通 API 请求也被标成 upgrade，upstream keepalive 8 完全失效，每个请求都新建 TCP 连接。用 map 后：真 WS 升级才透传 upgrade，普通请求走连接复用。

3. 补齐 assets 长缓存（线上缺失的那段）：


location ^~ /myweb/assets/ {
    expires 30d;
    add_header Cache-Control "public, max-age=2592000, immutable";
}

Vite 产物文件名带内容 hash，内容变文件名就变，所以可以放心 immutable——这是前端性能里性价比最高的一条配置。

4. posts.json / Content 用 no-cache：


location ^~ /myweb/Content/ {
    add_header Cache-Control "no-cache, must-revalidate";
}

文章会被管理台重发，不能用长缓存；但 no-cache + ETag 意味着没变时只回 304，配合前端 cache:'no-cache' 正好打满协商缓存。

架构层：音乐上 CDN

Music/ 563MB FLAC/m4a 原来全部由 ECS 直出。入门 ECS 带宽通常 1~5Mbps，一个用户放一首 40MB 的歌就能把带宽打满，全站跟着慢。音乐文件天生适合对象存储 + CDN（R2 免流量费），仓库里 upload-music-cdn.mjs 早就写好了，这次顺带把 VITE_MUSIC_BASE_URL 启用了。

1.4 部署过程踩的工具坑

这次环境本身也值得记录：

  • 本机没有 git：最后用 GitHub Desktop 内置的 git（%LOCALAPPDATA%\GitHubDesktop\app-*/resources/app/git/cmd/git.exe），配 credential.helper=wincred 用 Windows 凭据管理器完成 HTTPS 认证
  • PowerShell 不支持 heredoc：commit message 改成 git commit -F 消息文件
  • GitHub 直连被重置：curl 55 Send failure / 连接超时交替出现——典型的直连干扰。找到 Clash Verge（mihomo）在 127.0.0.1:7897 监听，给 git 加 -c http.proxy=http://127.0.0.1:7897 后一把推上
  • 远端领先本地 12 个提交：本地"未提交的 WIP"其实已经在别处推过了。放弃本地快照 rebase，改成以远端为基只叠加本次性能改动，避免把旧状态盖回新代码

1.5 结果与验证

部署后验证：


# assets 应有 immutable
curl -sI https://cyinc.ink/myweb/assets/ | grep -i cache-control
# ALPN 应返回 h2
python -c "import ssl,socket; c=ssl.create_default_context(); \
  c.set_alpn_protocols(['h2','http/1.1']); \
  s=socket.create_connection(('cyinc.ink',443)); \
  print(c.wrap_socket(s,server_hostname='cyinc.ink').selected_alpn_protocol())"

实测效果：重复访问速度约翻倍，首屏图片量从 ~3MB 降到 ~300KB 量级。

1.6 后续还能做的

  • 整站套 CDN：静态资源全量走边缘节点，ECS 只回源 API
  • Brotli 预压缩：构建时生成 .br，nginx brotli_static on，比 gzip 再省 ~15%
  • /uploads 直出：现在头像反代过 uvicorn，改成 bind mount + nginx alias 可以省一层 Python
  • Service Worker：预缓存 posts.json + 已读文章，弱网体验更好

1.7 小结

这次最大的收获不是哪条配置，而是方法：性能问题先测量再动手。curl -sI 看缓存头、ALPN 探测看协议、-w 看 TTFB——三条命令就能把"慢"定位到具体层。瓶颈最后落在"传输调度"而不是"服务器算力"，所以收益最大的是缓存策略和 HTTP/2，而不是升级机器。
