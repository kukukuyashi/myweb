1.1 Harness 概述

什么是 Harness？

Harness 直译为“马具”或“背带”，在软件工程中，它指的是支撑程序开发、测试、部署和监控的一整套工具、脚本和基础设施。

针对 AI Agent 开发，Harness 体系可以通俗地理解为 “Agent 的体检与上岗流水线”，它覆盖了从你写完代码到 Agent 正式上线服务的全过程，确保 Agent 在任何环境下都能稳定工作。

为什么要引入 Harness 体系？

AI Agent 与普通后端代码最大的不同在于：

  1. 依赖大模型（LLM） ：大模型的返回具有随机性，同样的输入两次结果可能不同。
  2. 依赖外部工具：Agent 需要频繁调用第三方 API（天气、数据库、搜索引擎），这些外部服务随时可能宕机。
  3. 输入不可控：用户可能会输入稀奇古怪、带有攻击性或格式错误的内容。

Harness 的核心目标就是提升 Agent 的 ==鲁棒性==。

==鲁棒性==（Robustness）：指系统在面对异常输入、外部故障或意外压力时，依然能够正常运行或优雅降级，不会轻易崩溃的能力。好比一根钢筋，用力掰只会弯曲而不会折断。

Harness 体系通常由以下几大支柱构成：

  1. 测试运行器：执行代码并报告哪些测试通过了，哪些失败了。
  2. 断言库：用来判断实际运行结果是否“等于”或“包含”预期结果。
  3. 模拟器：用来替代真实的外部依赖（如假装调用了一次天气 API）。
  4. 评估数据集：用来衡量 Agent“回答得好不好”的标准题库。
  5. CI/CD 流水线：自动化运行上述所有步骤的服务器脚本。

1.2 核心专有名词解释（必读）

在学习具体内容前，我们先扫清术语障碍：

专有名词 英文全称 通俗解释（大白话）
Harness Test Harness 测试“脚手架”，包含了运行测试所需的一切环境、数据和配置。
鲁棒性 Robustness 系统面对“搞破坏”或“乱输入”时，不崩溃、能兜底的顽强程度。
Mock Mocking “替身”。不调用真接口（如真实的 GPT-4），用假代码返回固定的测试数据，省电省心。
单元测试 Unit Testing 拆开 Agent 的最小零件（如一个加法工具函数）单独检测，不管周围环境。
集成测试 Integration Testing 把零件拼起来测试，看 Agent 能不能真的连上数据库或外部 API。
E2E 测试 End-to-End Testing 端到端，模拟真实用户从头到尾说一句话，看 Agent 最终反应如何。
Evaluation Eval “打分”。不仅测“对不对”，还测“好不好”，用于衡量回答质量、准确率。
CI/CD 持续集成/持续部署 代码一提交（git push），服务器自动帮你跑测试、打包、上线的自动化流程。

1.3 Agent 测试的“三层金字塔”

在 Harness 体系中，我们建议按照金字塔比例分配测试精力：底层多写（快），顶层少写（慢）。

1.3.1 第一层：单元测试（Unit Testing）

  • 测什么：测 JSON 解析函数、提示词模板拼接逻辑、异常捕获（try...catch）是否生效。
  • 特点：运行极快（毫秒级），不需要联网。
  • 专有名词：==断言==（Assertion）：指在测试中判断“实际结果”是否符合“预期结果”的代码行，如 expect(1+1).toBe(2)。

// 测试 Agent 的提示词构建函数
function buildSystemPrompt(tools) {
  return `你可以使用以下工具：${tools.join(', ')}`;
}

// 单元测试示例（Jest 风格）
test('buildSystemPrompt 应该正确拼接工具名称', () => {
  const result = buildSystemPrompt(['计算器', '日历']);
  // 这里的 expect(...).toBe(...) 就是“断言”
  expect(result).toBe('你可以使用以下工具：计算器, 日历');
});

1.3.2 第二层：集成测试（Integration Testing）

  • 测什么：测 Agent 调用真实 API 时，参数格式是否正确；收到返回后，解析是否报错。
  • 特点：需要配置测试环境（如测试用的 API Key），速度较慢。
  • 关键手段：==Mock（模拟）==：为了不让测试消耗真实 LLM 的 Token（计费）或被限流，我们常用 Mock 技术拦截网络请求。

// 集成测试中，使用 Mock 代替真实网络请求
const nock = require('nock'); // nock 是 Node.js 中专门用来拦截 HTTP 请求的库

test('Agent 调用天气 API 应返回格式化温度', async () => {
  // 1. 拦截真实请求，返回伪造的“假数据”
  nock('https://api.weather.com')
    .get('/city/beijing')
    .reply(200, { temp: 25, condition: 'Sunny' });

  // 2. 执行 Agent 逻辑
  const agent = new WeatherAgent();
  const result = await agent.getWeather('beijing');

  // 3. 断言结果
  expect(result).toContain('25');
});

1.3.3 第三层：端到端测试（E2E Testing）

  • 测什么：模拟用户完整对话“你好，帮我查下北京天气然后告诉我穿什么”。
  • 特点：通常需要使用真实的 LLM（如 Claude 或 GPT），但会设置较低温度参数保证稳定性。速度最慢，数量最少。

1.4 模拟（Mock）策略与隔离

为什么要做 Mock？（重点理解）

  • 省钱：每次单元测试都调用 GPT-4，一次 CI/CD 运行几百次，账单会很“感人”。
  • 省时：真调用需要等待网络延迟（2~5秒），Mock 是内存级的（微秒级）。
  • 造“极端场景”：真实 API 很难出现“超时”或“返回乱码”，但 Mock 可以轻易制造这些场景，用来测试 Agent 的 ==鲁棒性==。

常用 Mock 维度

  1. LLM 响应 Mock：直接模拟 claude.messages.create 返回固定字符串。
  2. 工具返回 Mock：模拟 search_engine.search 返回特定网页片段。
  3. 异常 Mock：模拟抛出 TimeoutError（超时错误），观察 Agent 是否会重试。

1.5 评估体系（Evaluation / Eval）

对于 AI Agent，很多问题是“没有标准答案”的。比如“写一首诗”，传统断言 expect(...).toBe(...) 完全无法工作。

什么是 Eval？

Eval（Evaluation）指使用预先标注好的测试集（黄金数据集）对 Agent 进行批量自动化评分，衡量“回答质量”。

常用评估指标（专有名词解释）

指标名称 解释
准确率 回答中正确事实的比例（如检索到的文档是否相关）。
相关性 回答与用户问题的匹配程度，通常由另一个大模型（如 GPT-4）打分。
幻觉率 衡量 Agent 是否编造了不存在的事实（越低越好）。
任务完成率 Agent 是否成功调用了正确的工具链并返回了结果。 

// 简单的 Eval 数据集结构（JSON）
const testDataset = [
  {
    input: '推荐一本关于中国历史的书',
    // 期望检查点（不要求逐字相同）
    required_keywords: ['史记', '资治通鉴', '明朝']
  }
];

// 运行评估：只看 Agent 回答是否包含关键词
testDataset.forEach(item => {
  const answer = await agent.chat(item.input);
  const pass = item.required_keywords.some(kw => answer.includes(kw));
  console.log(`测试项通过: ${pass}`);
});

1.6 Harness 实践：项目目录结构

下面是一个标准的 Claude Code 风格 Agent 工程目录，包含了 Harness 体系的所有要素：


my-awesome-agent/
├── src/                     # 源代码
│   ├── agent.ts             # 核心编排（Orchestration）逻辑
│   ├── tools/               # 工具函数（计算器、搜索等）
│   └── prompts/             # 提示词模板
├── tests/                   # 测试目录
│   ├── unit/                # 单元测试
│   ├── integration/         # 集成测试（带 Mock）
│   └── e2e/                 # 端到端测试（用真实模型）
├── eval/                    # 评估目录
│   ├── datasets/            # 黄金测试集（JSON/CSV）
│   └── evaluator.ts         # 打分脚本
├── jest.config.js           # 测试运行器配置
└── package.json

1.7 持续集成（CI）与自动化

在多人协作时，我们不能手动跑测试。需要引入 CI/CD 工具（如 GitHub Actions）。


# .github/workflows/harness.yml
name: Agent 质量流水线

on: [push, pull_request]

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v3
      - uses: actions/setup-node@v3
      - run: npm install
      - run: npm run test:unit        # 跑单测（必须全绿）
      - run: npm run test:integration # 跑集成测试
      - run: npm run eval:quick       # 跑轻量评估（防止模型退化）

1.8 综合练习：为“数学助教 Agent”编写 Harness

需求：

你开发了一个简单的数学 Agent，它只有一个加法工具 add(a, b)。请根据 Harness 思想，完成以下任务。

  1. 单元测试：测试 add 函数能否正确处理正数、负数。
  2. 异常测试：测试当输入非数字（如 add('a',1)）时，是否抛出了友好的错误提示。
  3. Mock 测试：模拟 LLM 告诉 Agent“请计算 1+1”，验证 Agent 是否调用了 add 工具。

答案（代码实现） ：


// src/tools/calc.js
function add(a, b) {
  if (typeof a !== 'number' || typeof b !== 'number') {
    throw new Error('参数必须是数字，请检查输入');
  }
  return a + b;
}
module.exports = { add };

// tests/unit/calc.test.js
const { add } = require('../../src/tools/calc');

describe('数学工具单元测试', () => {
  // 1. 正常场景测试
  test('正数相加正确', () => {
    expect(add(1, 2)).toBe(3);
  });
  test('负数相加正确', () => {
    expect(add(-1, -2)).toBe(-3);
  });

  // 2. 异常鲁棒性测试
  test('传入字符串应抛出友好错误', () => {
    // 为了测试“是否抛错”，需要用 toThrow 包裹
    expect(() => add('a', 1)).toThrow('参数必须是数字');
  });
});

// tests/integration/agent-flow.test.js
// 3. Mock 集成测试：验证 Agent 调用了工具
const { Agent } = require('../../src/agent');
const { add } = require('../../src/tools/calc');

// 模拟 LLM 的响应：假装模型告诉我们需要调用 add
jest.mock('../../src/agent', () => {
  return {
    Agent: jest.fn().mockImplementation(() => ({
      ask: jest.fn().mockResolvedValue('结果是 3')
    }))
  };
});

test('Agent 应能根据提示调用加法工具', async () => {
  const agent = new Agent();
  // 伪造一个调用场景：传入用户问题，Agent 内部应识别 "1+1"
  const response = await agent.ask('1+1等于几？');
  expect(response).toContain('3');
});

1.9 本章总结

概念 一句话总结
Harness 包含测试、模拟、评估在内的全套“保姆级”质量保障流水线。
鲁棒性 系统在恶劣输入或外部故障下的“抗揍”生存能力。
Mock（模拟） 用“假接口”代替“真接口”进行测试，为了省钱、提速、造极端场景。
单元 vs 集成 vs E2E 跑得快的多写（单元），跑得慢的少写（E2E），形成金字塔。
Evaluation（评估） 用题库给 Agent 打分，主要衡量幻觉率和任务完成率。
CI/CD 代码合并前自动触发的机器人测试员，卡住低质量代码上线。
